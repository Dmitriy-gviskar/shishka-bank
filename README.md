# Шишка Банк 🌲

Детское приложение финансовой грамотности. Цифровой слой над живой экономической игрой в лесу: кошелёк, переводы, задания, магазин, аукционы, лавки, гильдии.

**Продакшн:** https://elka-kvest-2026.ru

## Стек

| Слой | Технология |
|------|-----------|
| Клиент | Vanilla HTML/CSS/JS, PWA (service worker), SPA-навигация |
| Сервер | Node.js 18+, `server-pg.mjs` (прод), `server.mjs` (дев/SQLite) |
| База данных | PostgreSQL 16 (прод), SQLite `:memory:` (дев) |
| Хостинг | VPS Ubuntu, nginx + Let's Encrypt, systemd |
| APK | Android WebView wrapper, GitHub Actions сборка |

## Быстрый старт (локально)

```bash
cd client

# Дев-сервер (SQLite в памяти, без БД):
node --experimental-sqlite server.mjs
# → http://localhost:3777

# Прод-сервер (PostgreSQL):
DATABASE_URL="postgres://user:pass@host:5432/db" node server-pg.mjs
# → http://localhost:3777

# Тесты:
npm test
```

## Переменные окружения

## Деплой

### Подготовленная выкладка

Push в `main` запускает только тесты. Выкладка запускается отдельно через
`workflow_dispatch` с явным `deploy=true`, после успешного job `test` и через
production environment. Для среды production нужно заранее настроить required
reviewers в GitHub; одно имя environment не создаёт это правило автоматически.

Workflow загружает архив только в `/opt/shishka-incoming/<sha>`, проверяет SHA-256
и версию установленных ops-скриптов. `ops/deploy.mjs` готовит отдельный релиз,
включает обслуживание, останавливает сервис, требует проверенный checkpoint,
атомарно меняет `current` и проверяет БД/идентичность релиза. При ошибке после
остановки обслуживание остаётся включённым. Прямая запись в работающий каталог
и автоматическое возвращение старого непроверенного API запрещены.

До первого применения необходимо отдельно подготовить releases/current/shared,
nginx maintenance, systemd, секреты и backup config. Старый layout отклоняется.
Подробности и примеры конфигурации: `ops/README.md`.
Секреты SSH: `VPS_SSH_KEY`, `VPS_HOST`; root-пароль не используется.

## Применение миграций

Новые SQL клади в `client/migrations/` (деплой везёт только `client/*`). Сервер накатывает их при старте.
Не ходи на VPS по ssh и не гоняй `psql` с мака.

## Мониторинг

- `GET /api/ping` → `{"ok":true,"db":"ok","uptime":3600}`
- Health-check алерты: `ops/health-alert.sh` (каждую минуту через cron)
- Логи: `journalctl -u shishka -f`

## Доступ ведущего и восстановление

Все `/api/parent/*` требуют секрет `PARENT_PIN` в заголовке `x-parent-pin`.
При пустом PIN кабинет закрыт (503). Используйте длинный случайный секрет;
PIN вводится в кабинете ведущего и хранится только в sessionStorage текущей вкладки.
После 10 ошибок вход блокируется на 10 минут на IP в каждом серверном процессе.
Успешный детский вход не сбрасывает счётчик ведущего.

По умолчанию адрес клиента берётся из TCP-соединения. `TRUST_PROXY=1` можно
включить только за nginx, который перезаписывает X-Real-IP адресом клиента;
прямой доступ к Node.js при этом должен быть закрыт.

Восстановление по имени и IP отключено. Для смены устройства используйте код
с уже авторизованного устройства. Если код потерян, ведущий проверяет личность
человека вне приложения и выдаёт код из своего закрытого кабинета.

Назначение опекуна выполняет ведущий после проверки взрослого и его права
представлять ребёнка. Код входа, публичный код и имя не дают права назначать
себя опекуном. В кабинете доступны назначение, подтверждение и удаление связей.
Миграция `migration_guardian_verification.sql` сохраняет старые связи, но они
не дают доступа до повторного подтверждения ведущим. Уже выданные токены
устройств и коды входа эта миграция не отзывает.

Тесты можно направить в отдельную локальную БД через `PGPORT` и
`SHISHKA_TEST_DB` (имя должно начинаться с `shishka_test_`). Тесты пересоздают
только указанную тестовую БД. Например: `PGPORT=55439 SHISHKA_TEST_DB=shishka_test_access npm test`.

## Офлайн-паки и синхронизация

Без сети сохраняется заявка на пак, а не случайно сгенерированные клиентом карты.
Состав, редкость, гарант и награды определяет сервер при подтверждении покупки.
Локальное уменьшение доступного баланса — резерв заявки; реальное списание
и выдача происходят вместе в PostgreSQL. Слияния имеют локальное предварительное
отображение; после подтверждения коллекция сверяется с сервером.

Покупка и простое слияние требуют `nonce` (8–80 символов: буквы, цифры, `_`, `-`).
Он создаётся и сохраняется клиентом до отправки и остаётся тем же при повторах.
`/api/pack/open` и `/api/pack/offline` принимают только `{nonce, protocol: 2}`; список карт
от клиента запрещён. `apply_card_operation` одной транзакцией выполняет списание,
выдачу, счётчик, награды и сохранение результата. Повтор возвращает сохранённый
результат, включая карты; другое действие с тем же nonce получает 409.

Очередь в localStorage защищена Web Locks от конкурирующих вкладок. Браузер
без Web Locks не отправляет покупки паков и простые слияния: пользователь увидит объяснение.
Очередь привязана к коду аккаунта и переживает замену токена устройства.
Старая очередь текущего устройства переносится с сохранением nonce; выбранный
старым клиентом состав не передаётся серверу. Исторические паки, которые уже
отмечены в offline_pack_claims, но не имеют сохранённого результата, получают
409 для ручной проверки вместо повторного списания.

При HTTP-ошибках, обрыве связи, некорректном подтверждении и ошибках хранения
операции не удаляются автоматически. Баннер показывает очередь/ошибку и кнопку
повтора. Конфликтующая операция останавливает следующие, сохраняя их порядок.
Для конфликта нехватки средств нужно пополнить баланс и повторить отправку;
исторические неоднозначные операции требуют проверки ведущим.
Удалять записи из localStorage для устранения конфликта не следует: запрос
мог уже завершиться на сервере. Успешный результат хранится в серверном журнале
и не переигрывается после потерянного ответа. Очистка данных браузера пользователем
или удаление аккаунта остаются за пределами гарантий сохранности локальной очереди.

Миграция: client/migrations/migration_offline_operations.sql.
Новые клиент, сервер и миграция должны запускаться как совместимый комплект.
Эта версия несовместима со старым клиентом, отправляющим паки без nonce:
он получит HTTP 503 с предложением обновления, без списания средств.
Старые клиенты сохраняют 5xx в очереди; 4xx могли бы её молча удалить.

## Ошибка миграции при запуске

Все перечисленные миграции обязательны: отсутствующий или пустой файл,
ошибка чтения, подключения или SQL запрещают запуск HTTP-сервера.
В логе указывается проблемный файл, процесс завершается с кодом 78.
Кластер при таком коде останавливается целиком и не перезапускает воркер
внутренним циклом. Внешний менеджер процессов может иметь собственную политику
перезапуска; код приложения её не меняет.

Миграции выполняются последовательно на одном выделенном соединении с
PostgreSQL advisory lock. Каждая миграция — отдельная транзакция: при ошибке
её изменения откатываются, следующие файлы не запускаются. Успешные предыдущие
миграции остаются применёнными; после исправления сервер повторяет штатную
последовательность идемпотентных миграций. Фоновая работа и HTTP запускаются
только после успешного завершения всей последовательности.

## Неоднозначные старые слияния

Слияния из legacy-очереди не выполняются автоматически, включая записи,
которым прежняя версия переноса уже назначила новый nonce. Они сохраняются
с reviewRequired и блокируют последующие действия до проверки ведущим.
Новый nonce не доказывает, что старое слияние не было выполнено. Ведущий должен
сверить историю/карты и согласовать исправление; очистка очереди для обхода
проверки или повторное автоматическое исполнение не допускаются.

## Совместимость миграций гильдий

Boot-порядок включает `migration_guilds_v2.sql` и `migration_guilds_v3.sql` перед
`migration_guild_invites.sql`; файлы лежат в client/migrations и попадают в релиз.
Legacy-метрики определяются реальной полной SQL-логикой до её использования:
расследования читаются из transactions, игровые результаты — из mini_games.
Фиктивная таблица surprises и функция select 0 не требуются.

Миграция также обновляет старую create_guild из бэкапа: новая гильдия получает
основателя и запись истории. Повторное вступление не сбрасывает управляемую долю.
Выплата заказа записывает все выплаты/историю перед пересчётом достижений;
сумма распределения точна, гильдия остаётся открытой. Смена ролей не позволяет
лишить основателя его полномочий, права на изменение долей проверяются в SQL.
При повторном запуске миграций существующие финансовые данные не начисляются заново.

### Поколение карточных операций при восстановлении

Задайте в env `CARD_OPERATION_EPOCH` (UUID вне БД). Без него покупки паков и слияния
закрыты с 503. При обычном рестарте значение сохраняется; при ЛЮБОМ restore БД
обязательно создать новое до запуска всех воркеров, даже если env пришёл из backup.
Старые очереди не переписываются новым поколением и сохраняются для проверки.
Процедура и ограничения описаны в `ops/README.md`.

### Проверяемые игровые попытки

Мини-игры используют `game_attempts`: сервер хранит задания/ответы и расположение
карт памяти; клиент получает `attemptId` и отправляет ответ с индексом либо ход.
`score`/`expected` клиента не определяют прогресс и награду. Finish сохраняет результат,
дневной claim, кошелёк, историю и достижения в общей транзакции; retry идемпотентен.
Старый клиент без попытки не получает награду, ему нужно обновление и новая игра.

Блиц принимает ответы 30 секунд; забрать подтверждённый результат можно в пределах
30 минут с начала. В памяти 90 секунд — подсказка интерфейса: доиграть разрешено
до общего срока попытки 30 минут. При restore новый `CARD_OPERATION_EPOCH` также
блокирует прежние попытки игр, включая сохранённые результаты.
Сбор и обучение сборщиков сериализованы по кошельку; подарки блокируют оба кошелька
в одном порядке до проверки общего лимита 3 за день МСК, независимо от вида карты.
См. `docs/GAMEPLAY-FIXES-2026-11-09.txt` и новые регрессионные тесты.
