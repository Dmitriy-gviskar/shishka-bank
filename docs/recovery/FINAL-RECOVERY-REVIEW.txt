P1 ПОВТОРОВ ПОСЛЕ RESTORE — ЗАКРЫТ С ОБЯЗАТЕЛЬНЫМ УСЛОВИЕМ РОТАЦИИ
client/routes/cards.mjs сверяет b.epoch с внешним UUID CARD_OPERATION_EPOCH перед
карточным SQL для /api/pack/open, /api/pack/offline и /api/card/merge.
Отсутствующее/невалидное поколение сервера либо отсутствующее/чужое поколение
запроса означает HTTP503 без списания и выдачи. Без env приложение может отвечать
на ping и чтение, поэтому один успешный /api/ping НЕ подтверждает работу барьера.
GET /api/card/epoch доступен авторизованному клиенту. app.js ставит epoch только
на НОВУЮ операцию; read/sync/migration прежних записей его не подставляют.
Очередь сохраняется при 503; добавление нового поколения поверх старой очереди
запрещено. Legacy-слияния продолжают требовать отдельной проверки.

При каждом восстановлении, включая возврат C0/C1 на том же VPS, оператор создаёт
НОВЫЙ UUID вне БД и пишет его в защищённый app.env до запуска всех воркеров.
Значение из архивного env НЕ использовать. При обычном рестарте/откате только кода
с текущей БД epoch сохранять. Все экземпляры должны иметь одну метку; процессы
со старой меткой должны быть остановлены. Метку и связь с restore ID записать
в журнал восстановления, чтобы не принять старую за новую.
Барьер не умеет сам обнаруживать возврат дампа при повторном использовании env.
Он защищает от автоматического повтора, не от намеренного создания нового запроса
авторизованным пользователем и не от прямого SQL оператора. UUID не секрет.

Проверки: свежий импорт исходного SQL 1 ноября в новую БД; затем на отдельных
тестовых участниках моделировалась потеря receipts/claims и смена поколения.
Старые запросы всех трёх endpoint и запрос без epoch заблокированы без изменения
финансовых отпечатков. Новое поколение принято, retry возвращает тот же receipt.
Пять добавленных регрессий вошли в итоговые 166/166. Детали в
RECOVERY-BARRIER-REPORT.txt и recovery-barrier-backup-verification.json.
Ручной интерфейс сверки не добавлен. Заблокированные записи не удалять и не
переписывать новым epoch: сверка/компенсация — отдельная проверяемая процедура.
Это ограничение обслуживания затронутых аккаунтов, не основание отключать барьер.

ОГРАНИЧЕНИЯ ПРИЁМКИ
1. ops/deploy.mjs:95–98 и rollback после readiness сами удаляют maintenance-файл.
   Поэтому первый bootstrap выполнять отдельно; не запускать штатный deploy как
   инструмент подготовки закрытого первого восстановления. Это известная граница
   автоматизации, не повтор проблемы выкладки в работающий каталог.
2. Реальный тест backup выполняет pg_dump/pg_restore, но GPG/SSH/SCP/Git в нём
   заменены тестовыми исполнителями. Реальная доставка, decrypt и восстановление
   offsite на новой инфраструктуре ещё не доказаны. SUCCESS допускается только
   после реального end-to-end испытания. Наличие четырёх таблиц недостаточно для
   приёмки: дополнительно сверить данные, manifests uploads, секреты и запуск.
3. Онлайн-копия БД и uploads не атомарна. Для контрольных точек нужны остановленные
   писатели; backup cron и checkpoint выполнять последовательно под операторским
   регламентом/общим lock. В backup.mjs нет общего release lock с deploy.mjs.
4. Startup jobs сразу закрывают просроченные аукционы, усыпляют гильдии, могут
   начислить тестовую зарплату. Maintenance nginx не останавливает эти задачи.
   Отделять SQL baseline до запуска от состояния после старта; записывать дельту.
5. Старый VPS удалён, безопасного испытанного fallback релиза пока нет. Откат к
   уязвимому API неприемлем; при отсутствии fallback оставлять 503 и чинить вперёд.

ПОДТВЕРЖДЁННЫЕ ИСПРАВЛЕНИЯ
- /api/parent/* проверяет настроенный PIN независимо от детского токена;
  восстановление по имени закрыто; самопривязка опекуна запрещена;
  guardian API требует verified_at, прежние связи требуют проверки ведущим.
- Состав пака выбирает сервер; списание, выдача, награды и receipt проходят одним
  SQL-вызовом. Wallet row lock и ключ child/nonce защищают конкурентные повторы;
  различный payload при том же nonce отклоняется. Это верно при сохранном журнале.
- Очередь привязана к аккаунту, сериализуется Web Locks, сохраняет запрос до
  подтверждения operation_id; сбои сети/storage и refresh не считаются успехом.
  Legacy-слияния карантинируются, старые протоколы получают сохраняемый 503.
- CI tests обязательны перед manual deploy; push main не выполняет выкладку.
  Миграции сериализованы, каждый файл транзакционен; ошибка запрещает HTTP/background
  startup, exit 78 останавливает кластер. Вся пачка из 22 файлов НЕ одна транзакция.
- Staging в отдельный release, проверка checksum, current symlink, backup gate,
  readiness и release identity устранили старую in-place выкладку.
- Backup без plaintext fallback, с restore, GPG, offsite checksum и Git HEAD;
  ошибки дают ненулевой exit, SUCCESS создаётся последним.
- Гильдейские SQL-функции настоящие; v2/v3 включены в boot; founder/роли/доли,
  выплаты/метрики/история/сон проверены. Заглушка legacy и fake surprises удалены.

ОСТАВШИЕСЯ БЛОКЕРЫ И УСЛОВИЯ ДОПУСКА
B1 — Новый VPS не предоставлен/не проверен в этой задаче. Нужны IP, SSH fingerprint,
     права доступа, диск/ресурсы, firewall IPv4/IPv6, layout, unit/nginx/TLS/DNS.
     Без этого невозможно начать серверное восстановление. Старый VPS удалён.
B2 — Нет зафиксированного полного Git SHA и итогового артефакта с manifest assets.
     Нужна проверяемая сборка именно исправленного комплекта, а не прежнего main,
     с тестами в целевой среде. Source manifest не заменяет release manifest.
B3 — GPG fingerprint и offsite host в recovery JSON остаются placeholders.
     Нет подтверждённого реального end-to-end decrypt/restore независимой копии,
     контроля cron/checkpoint без пересечения, уведомлений и принятого retention.
     Блокирует публичное открытие; инфраструктуру бэкапов готовить в закрытом режиме.
B4 — Новые DB/PIN/SSH credentials и новый внешний CARD_OPERATION_EPOCH ещё должны
     быть установлены и проверены на VPS. Публичный ping не заменяет карточные
     negative/positive проверки. Старый UUID из config backup использовать нельзя.
B5 — Требуется принять срез 1 ноября и правила сверки периода после него. Данные
     более поздних операций не восстановлены барьером. Назначить ведущего для
     проверки очередей и старых guardian-связей, утвердить журнал компенсаций.
     Не требуется разблокировать все неоднозначные аккаунты ради запуска остальных:
     их очереди можно оставить в карантине с понятным порядком обращения к ведущему.
B6 — На новом хосте не выполнена закрытая приёмка: restore/22 миграции, повторный
     старт, epoch tests, доступ, PWA, файлы, startup дельты и checkpoint C1.
     После успешной локальной репетиции это проверка среды, а не открытый дефект кода.

Не являются самостоятельным запретом базового запуска:
- Нет безопасного испытанного fallback: принять аварийный режим 503 + исправление
  вперёд, либо подготовить совместимый fallback; уязвимый код не возвращать.
- Нет прежнего VAPID private/проверенных Telegram secrets: уведомления оставить
  выключенными и явно принять этот режим; включение требует отдельной проверки.
- Нет ручного UI очередей: затронутые записи остаются закрытыми до сверки.
- Не выполнен новый прогон прямо в этом документальном ревью: код не менялся,
  166/166 относится к проверенному совпадающему комплекту. При изменении сборки
  или среды повторить подходящие проверки и обязательный CI gate.
