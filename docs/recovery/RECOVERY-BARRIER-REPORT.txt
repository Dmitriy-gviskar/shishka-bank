Шишка Банк — серверный барьер повторов после восстановления БД
9 ноября 2026. Исправления применены в основной локальный проект, без деплоя.

Решение
Сервер проверяет внешний UUID CARD_OPERATION_EPOCH перед SQL покупок паков и
слияний: /api/pack/open, /api/pack/offline, /api/card/merge. Отсутствующее,
невалидное либо несовпадающее поколение означает HTTP503 без карточной операции.
SQL-транзакция списания/выдачи/receipt не изменена; её идемпотентность сохраняется.

Авторизованный GET /api/card/epoch сообщает текущую метку. Клиент сохраняет её
только в НОВОЙ записи. Read/sync/migration очереди никогда не заполняют epoch
старых записей. После неуспеха старая очередь остаётся на устройстве. Новая запись
с иным поколением не добавляется поверх старой очереди. Обновлён service worker.
Офлайн используется ранее полученный epoch; первая операция без известной метки
требует сети. Сам UUID не секрет и не заменяет аутентификацию.

ОБЯЗАТЕЛЬНЫЙ КОНТРАКТ ВОССТАНОВЛЕНИЯ
При каждом restore БД оператор обязан создать НОВЫЙ UUID вне БД и записать в
защищённый app.env ДО запуска всех воркеров, при включённом maintenance.
Значение из архивного env/config нельзя повторно использовать после restore.
При обычном рестарте/релизе с сохранной БД epoch, наоборот, сохраняется.
Все воркеры должны иметь одну метку; старые процессы останавливаются перед ротацией.
Без ротации внешней метки невозможно обнаружить возврат БД к прежнему состоянию
по той же восстановленной информации. Этот шаг — обязательный gate runbook.
Без настройки epoch карточные операции безопасно закрыты; остальные функции
приложения могут работать. Публичный запуск требует прежних инфраструктурных gates.

Старые записи нельзя «исправить» подстановкой нового UUID или удалением localStorage.
Ручной интерфейс сверки не добавлен: неоднозначные записи остаются заблокированными
до проверки ведущим. Барьер предотвращает автоматический повтор, но не возвращает
утраченные после 1 ноября данные. Прямые операторские записи в БД им не защищаются.

Проверка свежего бэкапа
Исходный SQL от 1 ноября с проверенным SHA-256 заново импортирован в НОВУЮ локальную
БД shishka_recovery_nov01_barrier_fix, не поверх прежнего тестового экземпляра.
Импорт без superuser; uploads из исходной копии; уведомления отключены, сеть loopback.
Исходные counts: users20 wallets19 transactions15625 user_cards5828.
Повторены реальные миграции гильдий, 920 сравнений метрик, полный запуск приложения
с 22 миграциями дважды; ошибок гильдейских background jobs нет.
На локальных тестовых участниках затем имитирована потеря receipts/claims,
поколение изменено между запусками: старые запросы трёх endpoint заблокированы,
запрос без поколения заблокирован; контрольные отпечатки финансовых таблиц неизменны
при отказе. Новое поколение допускает покупку; повтор возвращает ту же квитанцию
без второго списания/выдачи. Результат recovery-barrier-backup-verification.json.
Это новая реальная загрузка исходного бэкапа плюс моделирование потери журнала,
а не восстановление production или обещание сохранности отсутствующего периода.

невалидном env; protocol2 без epoch; сохранность очереди со старым epoch; handshake
не обогащает прежнюю очередь без epoch. Полный итоговый набор: 166/166 успешно, 0 ошибок, 0 пропусков.
