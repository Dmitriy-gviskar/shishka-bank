# Вход без кода и мультиарендность — дизайн

Дата: 2026-07-21 · Статус: согласован, к реализации

## Контекст

«Шишка Банк» работает на проде (elka-kvest-2026.ru) как ОДИН круг «LESFRIEND» с 10 детьми: ребёнок вводит персональный код (ТАЯ-01, ДЕМЬ-05…), код сохраняется в localStorage и уходит в каждом запросе заголовком `x-child-code`; взрослый входит по единому `PARENT_PIN` из env.

Решение Дмитрия: продукт выводится на рынок, вход по коду для этого не годится. Разбор текущего кода (`client/server-pg.mjs`) показал, что блокеров два, и второй тяжелее:

1. **Код — это одновременно логин, пароль и сессия.** Знаешь чужой код — ты этот ребёнок. Плюс `POST /api/onboard` по коду переписывает имя и породу дерева без подтверждения.
2. **Мультиарендности нет.** `PARENT_PIN` один на весь сервер; `GET /api/parent/children` (строка 509) отдаёт детей всей БД без фильтра по кругу; `add-child` и `add-prize` (511, 574) берут круг как `select id from circles order by created_at limit 1`. Две семьи на одном сервере увидят друг друга.

Цель: взрослый входит через Telegram, ребёнок — вообще ничего не вводит (устройство запомнено), круги изолированы, живой круг LESFRIEND продолжает играть без перерыва.

## Модель

Поверх существующих `circles / users / child_logins` добавляются три сущности:

- **`adults`** — взрослый как субъект: `id`, `tg_id` (unique), `name`, `created_at`. Заменяет собой PIN.
- **`memberships`** — `adult_id`, `circle_id`, `role` (`owner` | `leader`). Один взрослый может вести и свою семью, и лагерь; один круг может иметь несколько взрослых.
- **`device_tokens`** — `token` (случайный, 32 байта), `child_id`, `circle_id`, `created_at`, `last_seen_at`, `revoked_at`. Это то, что заменяет код у ребёнка.

`circles` получает колонку `kind` (`family` | `camp`) — механики одинаковые, различается только обвязка кабинета (семья: 1-3 ребёнка, свои задания; лагерь: много детей, библиотека шаблонов, массовые начисления). Оба сценария обслуживаются одним кодом.

### Потоки входа

**Взрослый (Telegram).** Бот `/start` → Mini App → сервер валидирует `initData` по HMAC с bot-token → находит/создаёт `adults` по `tg_id` → httpOnly-cookie сессия. Пароли и PIN не участвуют. Тот же канал даёт бесплатные пуш-уведомления («задание на проверке»).

**Ребёнок (device-token).** В кабинете «Подключить устройство» → одноразовая ссылка + QR с `link_token` (TTL 15 минут, сгорает при обмене) → ребёнок открывает на своём телефоне → сервер обменивает `link_token` на долгоживущий `device_token` → клиент хранит его и шлёт вместо `x-child-code`. Ребёнок не вводит ничего и кода не знает.

**Коды — запасной вход.** Экран «Войти по коду» остаётся (не на главной): для нынешних 10 детей и как аварийный доступ при потере устройства. `child_logins` не трогаем.

**Один телефон на двух детей.** На устройстве может лежать несколько `device_token`; переключение — существующий пункт «Сменить пользователя» на профиле.

### Контекст запроса

Единая точка резолва в `server-pg.mjs`: `device_token` (или legacy `x-child-code`, или сессия взрослого) → `{ child, circle, role }`. Все `/api/parent/*` фильтруются по `circle` из контекста. Это же закрывает нынешнюю утечку «кабинет видит всех детей БД».

## Этапы

Каждый этап деплоится отдельно; вход по коду работает до конца всех этапов, поэтому на любом шаге есть рабочий откат.

**Э1. Мультиарендность контекста** (без нового UI, снаружи ничего не меняется)
- миграция: `adults`, `memberships`, `device_tokens`, `circles.kind`;
- `ctx` расширяется до `{child, circle, role}`;
- все `/api/parent/*` получают фильтр по кругу; `add-child` / `add-prize` берут круг из контекста вместо «первый по created_at»;
- PIN-вход временно выдаёт сессию с ролью `leader` на круг LESFRIEND — обратная совместимость.

**Э2. Telegram-вход взрослого**
- бот + Mini App, валидация `initData` (HMAC-SHA256 по bot-token), httpOnly-cookie сессия;
- `parent.html` переезжает с PIN на сессию; PIN остаётся legacy-входом за флагом окружения;
- `/start` → «Создать семью» / «Создать круг-лагерь» → создание `circles` (`kind`) + `memberships(owner)`.

**Э3. Токен устройства для ребёнка**
- выдача `link_token` в кабинете (ссылка + QR — переиспользовать vendored `assets/qrcode.js`, он уже стоит для QR-кассы);
- обмен `link_token` → `device_token`; клиент шлёт токен вместо кода;
- guard в `app.js`: есть токен — пускаем; нет — экран «Подключить устройство / Войти по коду»;
- несколько токенов на устройстве + переключение профиля.

**Э4. Управление устройствами**
- список привязанных устройств у взрослого (имя ребёнка, последний вход), «отозвать» (`revoked_at`), «перевыпустить ссылку».

## Что переиспользуем

- `db/cards.sql` — образец идемпотентной миграции (`create table if not exists`, `on conflict … do update`, `create or replace function`). Новые миграции пишем так же.
- `client/server-pg.mjs`: обёртка роутов с целочисленным HTTP-статусом (после крит-фикса), `ctxCache` (код→ребёнок, 5 мин) — расширяется до токенов, `memoGet` — для справочников.
- `client/assets/qrcode.js` (kazuhikoarase) — генерация QR ссылки привязки, уже используется QR-кассой.
- `child_logins` и весь путь по коду — остаются нетронутыми как fallback.

## Безопасность и данные

- `device_token` — 32 случайных байта, в БД только хэш; передаётся заголовком, хранится в localStorage; отзыв через `revoked_at`.
- `link_token` — одноразовый, TTL 15 минут, привязан к `child_id`; повторный обмен отклоняется.
- `initData` Telegram проверяется по HMAC, с проверкой `auth_date` (не старше 24 часов).
- Все миграции additive; перед каждым деплоем — свежий дамп (существующий контур `/root/backup-shishka.sh`: локально + stukach + приватный git-репо).
- Проверка каждого этапа — через живой `https://elka-kvest-2026.ru/api/*`, а не только psql: прод обслуживает БД `shishka_prod`, connection-string брать из systemd-юнита.

## Вне этого спека (нужно до выхода на рынок, отдельным треком)

- Политика перс.данных и оферта: храним игровые имена детей и фото-отчёты на своём VPS (152-ФЗ).
- Монетизация: кто платит — родитель (B2C-подписка) или организатор (B2B2C за круг).

## Проверка

1. **Э1:** на копии БД завести второй круг с ребёнком → войти PIN-ом → кабинет показывает только детей своего круга; `add-child` кладёт ребёнка в нужный круг. Живой круг: `GET /api/state` по коду ребёнка отдаёт то же, что до миграции.
2. **Э2:** вход в Mini App из Telegram → сессия; `/start` создаёт круг обоих типов; PIN-вход всё ещё работает при включённом флаге.
3. **Э3:** в кабинете сгенерировать ссылку → открыть в другом браузере → приложение открылось без ввода; та же ссылка второй раз даёт отказ; через 15 минут — отказ; вход по коду по-прежнему работает.
4. **Э4:** отозвать устройство → следующий запрос с этого устройства получает 401 и экран подключения.
5. **Регресс на живом проде** после каждого деплоя: заход ребёнка, «Забрать подарок», выполнение задания, покупка в магазине.
