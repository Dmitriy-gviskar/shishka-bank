# Полные независимые бэкапы: Selectel S3 + SSH

Изменения локальные. Покупка, создание bucket, настройка удалённых площадок, очистка GitHub и деплой не выполняются автоматически.

## Формат и гарантии

Каждый уникальный snapshot содержит зашифрованный GPG bundle: custom pg_dump, весь appDir, uploads и configPaths, внутренний манифест с SHA-256. Перед отправкой выполняется настоящий pg_restore в отдельную временную БД и проверяются четыре ключевые таблицы. Онлайн-копия не гарантирует одновременное состояние БД и uploads: для согласованной точки используйте checkpoint при maintenance и остановленных приложении, workers и иных writers. Конфигурация restoreService должна указывать на отдельную тестовую БД/кластер с правами createdb, никогда не на production target.

Локальная копия, полный архив на SSH-offsite и полный архив в Selectel S3 сохраняются независимо. sourceFailureDomain/offsiteFailureDomain/s3.failureDomain должны обозначать три различных провайдера/домена отказа; строки проверяются, фактическую независимость аккаунтов и инфраструктуры подтверждает оператор. SSH на том же VPS не является независимым бэкапом. GitHub хранит только metadata-v2/<snapshot>.json (без конфигурационных секретов), не полный архив. Старые backups/history не удаляются.

SUCCESS появляется только после восстановления scratch-БД, шифрования, ssh sha256sum, загрузки S3 с If-None-Match:*, скачивания точной VersionId и полной сверки размера/SHA-256, сохранения receipt на обеих площадках и подтверждённого Git push. ETag не считается SHA-256. Ошибки не удаляют прошлые копии; незавершённые multipart uploads прерываются по возможности. Полные объекты после поздней ошибки могут остаться без SUCCESS: проверить вручную, не считать успешным cron. Сбой после Git commit/push требует сверить HEAD, удалённую ветку и receipt перед следующим запуском; force-push запрещён. Зеркало должно быть чистым и синхронным до запуска, чтобы не отправить старые архивные коммиты.

## Подготовка до первого запуска

1. Сохранить архивы 1 ноября, релиз и ключ расшифровки на независимый носитель. Не удалять прежнюю GitHub-копию.
2. Установить Node 24, PostgreSQL client 16, GNU tar, OpenSSH, GnuPG и AWS CLI (проверено awscli 1.46.3). Скопировать ВСЕ ops/*.mjs включая s3.mjs; сверить SHA-256 релиза. Для системы выделить закрытый каталог конфигурации; процессы не должны писать в него.
3. В отдельном Selectel аккаунте подготовить приватный bucket, включить versioning; endpoint и region взять из панели текущего региона, не копировать устаревшие адреса. HTTPS обязателен. API-ключу выдать только нужные List/GetBucketVersioning, Put/GetObjectVersion и multipart/abort права на выделенный prefix; не выдавать удаление версий/изменение bucket. ACL public-read не используется.
4. Создать приватные файлы credentialsFile и configFile из backup.example.json, оба chmod 600. Credentials: [shishka-backup] с aws_access_key_id и aws_secret_access_key. Config: [profile shishka-backup], region из панели, s3/addressing_style = path. Не помещать ключи в Git, shell history, URL или manifest. app configPaths не должны включать AWS credential files или приватный GPG-ключ. Приватный ключ держать вне VPS, минимум две офлайн-копии; на VPS только публичный ключ шифрования.
5. Подготовить SSH-offsite у третьего провайдера, отдельный аккаунт и каталог, host key закрепить в known_hosts, закрытые права и достаточно места. Независимые MFA/recovery credentials хранить отдельно.
6. Инициализировать чистое зеркало Git метаданных с main и подтверждённым origin. Старое зеркало со старыми неопубликованными коммитами не использовать без разбора. Не применять git add . или force-push. Старую историю GitHub сейчас НЕ переписывать. Если нужны физическое удаление больших архивов из истории и сокращение GitHub-хранилища — сначала две реальные независимые проверенные копии и отдельное согласование rewrite. .gitignore не удаляет уже отслеживаемые файлы.
7. Заполнить backup.example.json и backup в deploy.example.json одинаковой схемой. На время изменения схемы остановить старый cron; запускать только одну версию. Проверить отсутствие активного бэкапа. .backup.lock при аварии не удалять автоматически: сначала убедиться, что владельца/процесса больше нет.
8. Выполнить checkpoint вручную, проверить SUCCESS и receipt на всех площадках, затем независимое восстановление каждой удалённой копии. Только после этого включать расписание и оповещения на ненулевой exit/просроченный SUCCESS. Retention не автоматизирован: согласовать объём, сроки и защищённые версии; bucket versioning сам по себе не защищает от владельца с DeleteObjectVersion. Object Lock при необходимости настроить отдельно до эксплуатации и испытать восстановление.

## Проверка и восстановление копии

Из доверенного Git receipt выбрать copies[kind=s3], используя endpoint/bucket/key/versionId/bytes/sha256. С конфигурацией AWS выше скачать:

    AWS_SHARED_CREDENTIALS_FILE=/root/.aws/shishka-credentials AWS_CONFIG_FILE=/root/.aws/shishka-config aws --profile shishka-backup --endpoint-url HTTPS_ENDPOINT --region REGION s3api get-object --bucket BUCKET --key KEY --version-id VERSION_ID /private/restore/bundle.tar.gpg

Для SSH независимо скачать bundle.tar.gpg и receipt из copies[kind=ssh].directory. Для КАЖДОЙ копии сравнить размер и sha256sum с доверенным receipt, а не только с файлом рядом с архивом. Разные UUID snapshots не смешивать. gpg --output bundle.tar --decrypt bundle.tar.gpg на изолированном recovery-хосте; проверить список tar на абсолютные пути, .. и ссылки до распаковки в пустой каталог, сверить hashes внутреннего manifest. Извлечь code/uploads/config, pg_restore --exit-on-error --no-owner в НОВУЮ БД. Проверить таблицы, приложенные файлы и миграции, запустить приложение локально. Никогда не восстанавливать поверх работающей БД. Перед запуском любого worker после КАЖДОГО восстановления обязательно создать НОВЫЙ CARD_OPERATION_EPOCH во внешней конфигурации. Обычный рестарт/откат только кода epoch не меняет.

Откат операции резервного копирования: оставить старые проверенные копии, отключить новый cron, исправить конфигурацию и повторить с новым snapshot ID. Возврат старого backup.mjs без S3 возвращает большие Git uploads — не включать его cron. Откат приложения/БД выполняется по основному runbook в maintenance с новой epoch при восстановлении БД.

Справка: https://docs.selectel.ru/s3/objects/conditional-requests/ ; https://docs.selectel.ru/api/object-storage-s3/ . Реальные IAM/endpoint/VersionId/retention и аварийное восстановление из облака остаются обязательным приёмочным испытанием после выдачи доступов.
