# Эксплуатация Шишка Банка

Деплой из рабочей папки, `rsync` поверх работающего клиента и прямой рестарт
без checkpoint больше не являются штатным путём. Эти изменения подготовлены
локально; VPS, cron, nginx, systemd и GitHub environment ещё нужно настроить
отдельно после разрешения на работы.

## Первичная подготовка (не запускать старый deploy job)

1. Подготовить root-owned `/opt/shishka/releases`, `/opt/shishka/current` (symlink
   на проверенный релиз), `/opt/shishka/shared/uploads` и
   `/var/lib/shishka`. Права должны позволять сервисной группе читать код,
   но писать только в uploads. Код релизов root-owned, group read/execute.
2. Systemd: WorkingDirectory должен быть ровно `current` из config, ExecStart
   должен ссылаться на `current/server-pg.mjs` или `current/server-cluster.mjs`.
   Настроить закрытый EnvironmentFile: DATABASE_URL, длинный PARENT_PIN,
   TRUST_PROXY согласно проверенному nginx. Прямой доступ к Node извне закрыт.
3. Nginx должен проверять maintenance-файл и возвращать API HTTP 503 + JSON и
   Retry-After. Не выдавать 200/HTML вместо API. Диагностический URL через nginx
   обязан давать 503 при установленном флаге. Loopback Node используется для
   готовности и /release.json. Не очищать пользовательские данные PWA.
4. Проверить все дополнительные процессы/cron, способные писать в БД или uploads:
   они должны быть остановлены на время checkpoint. Скрипт проверяет основной
   unit, но не может обнаружить произвольного внешнего писателя.
5. Установить Node 24, Python 3, npm, PostgreSQL client совместимой версии,
   tar, GPG, SSH/SCP, Git, sha256sum. Публичный backup GPG-ключ должен быть проверен
   и пригоден для batch encryption. Приватный ключ хранить отдельно, проверить
   возможность расшифровки при репетиции восстановления.
6. Установить `runtime.mjs`, `backup.mjs`, `deploy.mjs`, `backup-shishka.sh`
   в root-owned `/opt/shishka-ops`. Workflow сравнивает SHA-256 трёх модулей
   с проверенной версией из репозитория; несовпадение блокирует запуск.
7. Создать закрытые JSON config по `backup.example.json` и `deploy.example.json`.
   Это примеры, не готовая конфигурация VPS. Фактическое имя БД проверить через
   current_database(), не выводить из строки URL. Конфиги/PG service/.pgpass — 0600.
8. В GitHub создать/проверить protection rules production environment, required
   reviewers и SSH secrets. Push в main теперь только проверяет тесты.
   Выкладка требует ручного workflow_dispatch с deploy=true.

## Релиз

Workflow после полного npm test пакует `client/` и `.nvmrc`, не включая uploads,
node_modules или env. Архив поступает в incoming/<commit-sha>, не в runtime.

`deploy.mjs` отклоняет старый layout и неверный checksum, захватывает host lock,
распаковывает только обычные файлы/каталоги client и .nvmrc (ссылки, traversal,
специальные файлы и uploads запрещены), ставит зависимости в отдельном релизе.
Затем: maintenance -> stop -> проверенный checkpoint -> atomic current switch
-> start -> проверка ok/db и release ID -> снятие maintenance.

При подготовительной ошибке ссылка/работающий релиз не меняются. При ошибке
после остановки сервис остаётся остановленным, maintenance не снимается.
Файл deployment.json хранит причину, предыдущий путь и checkpoint. Частичный
каталог релиза остаётся для диагностики; повторное использование SHA без
проверенного ручного удаления не разрешается. После аварийного завершения
процесса lock может остаться: проверить отсутствие процесса перед удалением.
Не удалять lock/maintenance для «починки» без проверки состояния.

## Строгие бэкапы

Cron должен вызывать установленный `/opt/shishka-ops/backup-shishka.sh`;
он делает exec Node и сохраняет неуспешный exit status. Config по умолчанию
`/root/shishka-backup.json`, другой путь через SHISHKA_BACKUP_CONFIG.
Legacy `/root/backup-shishka.sh` сам не обновляется — при первичной настройке
нужно заменить cron/установленную копию. Никаких sed-подстановок имени БД нет.

Для каждого бэкапа создаётся новый timestamp+UUID, без перезаписи старых копий.
В комплект входят custom pg_dump, полный код, uploads и явный перечень config.
Дамп реально восстанавливается в уникальную БД shishka_restore_<uuid> через
отдельный PG service; используются --exit-on-error и проверка ключевых таблиц.
Восстановленная scratch БД удаляется; рабочая БД не используется как цель restore.
У restore-role должно быть право создавать/удалять только согласованные тестовые
БД на валидационном сервере. Эта услуга и её ресурсные лимиты требуют подготовки.

Комплект шифруется GPG; fallback к открытому дампу отсутствует. Нужны обе
независимые копии: SSH/SCP offsite с проверкой SHA-256 и Git mirror с подтверждением
remote HEAD. В Git добавляются только зашифрованные bundle и checksum конкретного
snapshot. Репозиторий должен оставаться приватным, включая старую историю.
Только после всех проверок атомарно появляется локальный SUCCESS.json.
Любая ошибка dump/archive/restore/encryption/transfer/checksum/push возвращает
ненулевой статус; старые копии не удаляются. Автоматической ротации больше нет:
планировать отдельную retention-процедуру, не удаляющую релизные checkpoints.

Online backup из cron помечен mode=online: он не обещает атомарную согласованность
БД и меняющихся uploads. Deployment вызывает mode=checkpoint только после
maintenance и остановки сервиса. Только такой checkpoint допускается к переключению.

## Откат кода

`deploy.mjs <config> rollback <full-commit-sha>` работает только для релиза,
явно включённого оператором в approvedFallbacks (SHA -> checksum архива) после
проверки сохранения всех исправлений доступа и идемпотентности. По умолчанию
список пуст. Нельзя автоматически откатиться на старую уязвимую версию.

Откат использует тот же host lock и maintenance, переключает код целиком и
проверяет release ID/БД. При ошибке обслуживание остаётся включённым. БД и
uploads автоматически не восстанавливаются: новые receipts и транзакции
сохраняются. Восстановление данных после открытия трафика требует отдельной
сверки и согласования; не стирать журнал nonce или пользовательские очереди.

## Старые слияния

Legacy-слияния, в том числе уже перенесённые в offv2 с синтетическим nonce,
помечаются reviewRequired и не отправляются. Они остаются в хранилище и видны
в баннере. Проверить историю карт/действий и связаться с ведущим; не выдавать
новый ID и не повторять старую операцию автоматически. Штатный ручной интерфейс
исправления неоднозначных старых историй в этой задаче не добавлялся.

## Переход старых вкладок

Карточные запросы новой очереди помечены protocol=2. Предыдущие вкладки без
этого протокола, включая синтетические nonce из прежнего переноса, получают
HTTP 503 без исполнения. Так старый механизм синхронизации сохраняет запрос,
а не удаляет его по 4xx. После обновления PWA новые обычные записи получают
protocol=2 с прежним nonce, а legacy-слияния остаются на проверке. Сервис worker
обновлён; очищать localStorage для обновления нельзя.

## Барьер очередей при восстановлении БД

В env сервиса обязателен `CARD_OPERATION_EPOCH`: UUID, созданный оператором вне БД.
Если он отсутствует/невалиден, чтение остаётся доступным, но паки и слияния возвращают
503 без исполнения. Перед ПЕРВЫМ запуском восстановленной БД всегда создать НОВЫЙ UUID
(например `node -e 'console.log(require("node:crypto").randomUUID())'`) и записать в
защищённый app.env. Не использовать значение из восстановленного env/config архива.
В обычном рестарте/деплое без восстановления БД UUID сохранять. На всех воркерах и
экземплярах должен быть один UUID; старые процессы остановить до изменения.

Новое поколение выдаётся авторизованному клиенту GET /api/card/epoch. Клиент ставит
его только при создании НОВОЙ операции. При offline используется последнее известное
поколение, поэтому такие операции после restore тоже блокируются. Старые записи
не переписываются при обновлении, handshake, reload или retry; очередь сохраняется
при 503, новые действия при несовместимой очереди запрещены до проверки ведущим.
Это барьер аварийного повтора, а не секрет/замена авторизации. Он не восстанавливает
утраченные данные. Работа с БД напрямую требует отдельного операторского контроля.

При восстановлении: maintenance -> остановить всех писателей -> сохранить аварийный
snapshot -> восстановить в новую БД/uploads -> новый UUID вне дампа -> запуск за 503
-> проверить старые запросы без epoch/со старым epoch и отсутствие списаний ->
проверить новую операцию и retry -> сверить очереди -> открыть трафик.
Без ротации внешнего UUID нельзя отличить прежнее поколение после восстановления
дампа, который уже содержит receipts. Этот шаг — обязательный gate восстановления.
Ручной интерфейс сверки очередей не добавлен: не удалять их и не подставлять новый
epoch в старые body. Неоднозначные операции остаются закрытыми до отдельной сверки.

## Релиз исправлений игровой экономики

Boot содержит 23 файла, включая migration_gameplay_integrity.sql. Он создаёт
private game_attempts/game_daily_claims и реальные SQL-функции ответов/ходов/finish.
Приложение работает ролью владельца схемы/миграций; PUBLIC не получает доступ
к ключам ответов и новым RPC. При отдельной runtime-role нужно явно согласовать
минимальные grants; не открывать эти функции игрокам напрямую.
На закрытой приёмке проверить попытку, ответы, finish/retry и старый epoch503;
старое завершение только с score без attemptId не должно выдавать награду.
Обычный restart сохраняет epoch; каждый restore (включая возврат к checkpoint)
создаёт новое поколение ДО запуска. Новую миграцию можно применять повторно:
сохранённые attempts/claims/results не стираются.
Релиз 0b0048a не является безопасным fallback игровой экономики: в нём остаются
подтверждённые гонки и доверие score. approvedFallbacks оставлять пустым до
испытания версии, сохраняющей все фиксы, включая эти. При аварии — maintenance
и исправление вперёд; новые receipts/claims не удалять.
